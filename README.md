# TendExtensions

The public registry of official [Tend](https://github.com/Tend-Stack) panel
extensions.

Source of truth for this registry is Gitea
(`https://j.santanafam.com/Rubirosa/TendExtensions`, private, CI origin). Every
push to `main` there is mirrored verbatim to GitHub
(`https://github.com/Tend-Stack/TendExtensions`, public) by the same
publish-then-release pipeline every Tend repository uses. **Panels consume
only the GitHub side** — the built `registry.json`, its signed envelope, and
the per-extension ZIP packages attached to each `registry-<sequence>` GitHub
release.

## What's in this repository

```
extensions/<id>/          one folder per extension (id = manifest id)
    extension.json         schema-2 manifest (id, name, version, permissions,
                            UI/runtime declaration, integrity map)
    listing.json            store listing fields the panel catalog needs
                            beyond the manifest (publisher, category,
                            features, requirements, release notes, ...)
    README.md, icon.*, *.js, ...

tools/
    build.py                 validates every extension, rebuilds the
                              integrity map from the files on disk, builds
                              deterministic ZIPs, writes dist/registry.json
    sign.py                   signs dist/registry.json into the published
                              envelope (dist/tend-extension-registry-v1.json)
    validate_with_panel.py    runs every built package's manifest through
                              the panel's own manifest parser
    release.py                creates/updates the GitHub release for a
                              registry sequence and uploads its assets

scripts/publish-verified-main.py   mirrors the exact verified Gitea commit
                                    to GitHub main (same script every Tend
                                    repo uses)

.gitea/workflows/ci.yml    build → publish_github → release, main only
                            for the last two jobs
```

`dist/` is generated by CI and is not committed — see `.gitignore`.

## registry.json (schema 1)

Generated by `tools/build.py`, never hand-edited:

```json5
{
  "schema": 1,
  "registry_id": "tend-extensions",
  "sequence": 42,            // git rev-list --count HEAD on main
  "revision": "<40-hex commit sha>",
  "generated_at": 1758000000,
  "extensions": [
    {
      "id": "host.tend.calculator",
      "name": "Calculator",
      "version": "3.0.0",
      "publisher": "TEND Stack",
      "description": "...",
      "category": "productivity",
      "featured": true,
      "reviewed": true,
      "features": ["..."],
      "requirements": ["..."],
      "permissions": ["storage"],
      "release_notes": "Initial registry release.",
      "path": "extensions/host.tend.calculator",
      "homepage": "https://github.com/Tend-Stack/TendExtensions/tree/<revision>/extensions/host.tend.calculator",
      "package": {
        "name": "host.tend.calculator-3.0.0.zip",
        "bytes": 62571,
        "sha256": "<64 hex>"
      }
    }
  ]
}
```

Entries are sorted by `id`. The package download URL is derived by the
consumer, never carried in the payload:

```
https://github.com/Tend-Stack/TendExtensions/releases/download/registry-<sequence>/<package.name>
```

## Signed envelope

`dist/tend-extension-registry-v1.json` wraps `registry.json` in the same
envelope shape the panel already verifies for the Notes release feed
(`extension_release_discovery.py`, `_verify_envelope`), with its own domain
separation string and pinned key:

```json
{
  "schema": 1,
  "key_id": "51f460b512853065",
  "payload": { "...": "the registry.json object above, plus issued_at/expires_at" },
  "signature": "<base64 Ed25519 signature>"
}
```

`signature = Ed25519.sign(b"tend-extension-registry-v1\n" + canonical_payload)`,
where `canonical_payload = json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=True)`.
The payload is valid for 365 days from `issued_at`. The pinned public key is
`yi68zm6gAuttvyH9TUyo/oiC002cCzgrGHbjp8BdxOA=` (base64, raw 32 bytes),
`key_id = sha256(public key bytes)[:16]` hex = `51f460b512853065`.

## How panels consume this registry

A Tend panel's `extension_registry` service polls the GitHub Releases API for
`Tend-Stack/TendExtensions`, finds the newest `registry-<sequence>` tag,
downloads `tend-extension-registry-v1.json`, verifies it against the pinned
public key above (domain, schema, validity window, monotonic sequence), and
merges the verified entries into its built-in extension catalog. Registry
entries win over built-in catalog entries with the same id; unrelated
built-in entries are untouched. A disabled or unreachable registry never
breaks the store — the built-in catalog still lists.
